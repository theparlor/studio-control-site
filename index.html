In the world

Your studio hardware, verified.

studio-control unifies Wave Link, Philips Hue, Govee, OBS, Teams, and OBSBOT under one control surface. Its defining principle: software state is a hypothesis — the physical world is the fact. Every command closes the loop or tells you it couldn't.

The problem it solves

A mute toggle that silently fails during a client call is a career risk.

Six pieces of hardware, six vendor APIs — some public, some reverse-engineered, some open-loop by design. The moment you add a Stream Deck button, you've made a promise to yourself that the rack will do what the button says. studio-control exists to keep that promise: it tracks state, detects divergence, and surfaces the gap before it surfaces on your client's face.

The question isn't "did the command send?" It's "did the world change?"

What makes it different

The physical-world boundary is a first-class constraint.

The rule the whole product is built around

Software state is a hypothesis. The rack is the fact.

Most control software assumes the command landed. studio-control refuses that assumption. Every API call that can return a verification signal does — and when the ACK doesn't come back within the SLO window, a signal fires. For the surfaces that cannot be verified (Teams osascript, OBSBOT keyboard injection), the open-loop nature is treated as a known architectural gap, surfaced to the operator verbatim, never papered over. The product holds two classes of command explicitly:

Closed-loop commands

Wave Link, Hue, Govee, OBS — state is confirmed by the device. Divergence emits a signal. You know when it worked.

Open-loop commands

Teams, OBSBOT — injection-only, unverifiable. Treated as a hypothesis, labeled as such, never silently assumed to have landed.
